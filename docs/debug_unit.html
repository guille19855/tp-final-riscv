Debug Unit por UART

Recibe comandos de la PC, carga el programa sin resintetizar, ejecuta en modo continuo o paso a paso frenando el procesador con su enable, y envía PC, registros, latches y memoria de datos usada. Del lado de la PC, una CLI y una interfaz gráfica en Python.

Protocolo

Cada comando es un byte; las palabras de 32 bits viajan en little-endian.

ComandoEfectoRespuesta
L N0 N1 + N palabrasCarga el programa. El CPU queda en reset mientras tanto, y el mapa de memoria usada se borra en paralelo.K
RReset del CPU: PC, registros, latches y ciclos en 0. La memoria de datos se conserva.K
CContinuo hasta el HALT. Cualquier byte que llegue mientras corre lo pausa.volcado
SUn ciclo de reloj.volcado
DVolcado sin ejecutar.volcado
IRelee el programa cargado.I + N + palabras
otroComando inválido.?

Volcado: 'D' + 51 palabras + memoria

PalabraContenido
0 · 1 · 2PC · ciclos · estado (bit 0 = HALT)
3 – 34x0 … x31
35 – 38IF/ID: pc, pc+4, instr, válido
39 – 44ID/EX: pc, pc+4, rs1, rs2, imm, control
45 – 47EX/MEM: result, rs2, control
48 – 50MEM/WB: result, read_data, control
luegopares (dirección, dato) … 0xFFFFFFFF

Memoria de datos usada

Se interpretó como las palabras que escribió algún store. Un mapa de bits en hardware (dmem_used.v, 1024 × 1 en LUTRAM, 69 LUT) marca cada palabra escrita; el volcado recorre el mapa y manda solo las marcadas. Con 1024 flip-flops harían falta además un decodificador y un mux de 1024 entradas.

El volcado entero es de unos 220 bytes: a 115200 baudios tarda unos 20 ms, imperceptible al ir paso a paso.

La máquina de estados

Frenar justo en el HALT

// combinacional: baja en el MISMO ciclo
// en que el ebreak llega a WB
assign cpu_en = ~program_done &
                (state == RUN | state == STEP);

// ciclos ejecutados
always @(posedge clk)
  if (cpu_reset)   cycles <= 0;
  else if (cpu_en) cycles <= cycles + 1;

Las palabras fijas del volcado

always @(*)
  if      (item == 0)  fix_word = pc;
  else if (item == 1)  fix_word = cycles;
  else if (item == 2)  fix_word = {31'd0, done};
  else if (item < 35)  fix_word = reg_data;
  else                 fix_word = latch_data;

assign reg_addr  = item - 3;    // x0..x31
assign latch_sel = item - 35;   // 16 palabras

El sincronizador de rx (dos flip-flops) es la única excepción a "todo resetea a 0", y es a propósito: la línea en reposo vale 1, y un 0 después del reset la UART lo tomaría como un bit de start falso.

Verificación

tb/top/top_core_tb.v prueba el sistema como lo ve la PC: un modelo de UART arma cada bit en la línea rx y lee la línea tx, sin tocar señales internas para manejar el sistema.

  • Comando inválido, volcado después del reset, carga y relectura con I.
  • Paso a paso decodificando los 16 latches y comparándolos con las señales internas. Los programas de hasta 100 ciclos se recorren enteros.
  • Continuo: ciclos, registros y memoria usada iguales al modelo de referencia, y el pipeline vacío al final.
  • C y S después del HALT no ejecutan nada; reset; recarga; un lazo infinito pausado con un byte.

Los 28 programas pasan. Para validar el propio testbench se introdujeron 7 fallas a propósito en la Debug Unit (mutaciones) y las detecta todas. En la placa, debug_cli.py verificar hace las mismas comparaciones con los 28 programas a 85 MHz.

Síntesis

La Debug Unit ocupa 288 LUT y 218 flip-flops; el mapa de memoria usada, 69 LUT (64 como LUTRAM). Es alrededor del 15 % del sistema.

Preguntas para la defensa

  1. ¿Cómo se implementa el paso a paso sin tocar el clock?Con el enable: todos los flip-flops del procesador son FDRE con CE = cpu_en, y en el estado STEP cpu_en vale 1 durante un solo ciclo. El clock nunca se compuerta.
  2. ¿Cómo garantizan que el pipeline queda vacío al terminar?ID deja de buscar al ver el ebreak, así que detrás de él solo entran burbujas. Cuando llega a WB, program_done sube y cpu_en baja en ese mismo ciclo, porque es combinacional: nada más avanza.
  3. ¿Qué es la "memoria usada"?Las palabras escritas por stores desde la última carga. Las marca un mapa de bits en hardware y el volcado manda solo esas, con su dirección.
  4. ¿Cómo se leen ~500 bits de latches con una UART?Con un mux en cpu_top que entrega una palabra de 32 bits por vez; la Debug Unit pide las 16 en orden. El control se empaqueta en una palabra por latch y la PC lo decodifica con la misma tabla.
  5. ¿Por qué el sincronizador en rx?La línea viene de otro dominio (la PC) y puede cambiar justo en el flanco: un flip-flop solo podría quedar metaestable. Con dos, el segundo casi siempre ve un valor estable.
  6. ¿Cómo se pausa un programa que no termina?En modo continuo, cualquier byte recibido detiene la ejecución y responde con un volcado. La GUI lo hace con el botón Pausa, desde un hilo aparte.
  7. ¿Cómo cargan otro programa sin resintetizar?Con L: la Debug Unit escribe la memoria de instrucciones por su puerto B mientras mantiene al procesador en reset.
