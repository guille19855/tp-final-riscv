Timing del procesador

Cuál es el camino combinacional más largo, cuánto mide y cómo se acortó: la frecuencia máxima post-síntesis pasó de 64,9 a 90,5 MHz y la placa corre a 85 MHz, sin cambiar la cantidad de ciclos de ningún programa.

Cómo se midió

El docente pidió sacar la frecuencia máxima del análisis post-síntesis. synth/measure.tcl sintetiza el sistema completo (procesador, Debug Unit y UART) con un reloj deliberadamente exigente de 10 ns y lee el peor slack:

fmax = 1 / (10 ns − WNS)          // WNS negativo = no llega a 10 ns
antes:   1 / (10 + 5,407) = 64,9 MHz
después: 1 / (10 + 1,055) = 90,5 MHz

Después se implementa el mismo diseño como referencia (place & route) y se valida la frecuencia final en el proyecto completo, con el Clock Wizard y los pines.

Las dos optimizaciones

1. Comparador de igualdad para beq/bne

// antes: la resta de la ALU y su zero
// branch_cond = BNE ? ~alu_zero : alu_zero;

// después: XOR por bit + árbol de AND
wire operands_eq = (a_fwd == b_fwd);
wire branch_cond = (funct3 == `F3_BNE)
                  ? ~operands_eq : operands_eq;

No pasa por el mux ALUSrcB (los saltos siempre comparan rs1 con rs2), ni por un acarreo de 32 bits, ni por el OR del zero.

2. Burbuja solo de control

// a) reset O burbuja -> 0     (22 FF)
if (reset || (en && bubble)) begin
  id_ex_rs1 <= 0; id_ex_rs2 <= 0; id_ex_rd <= 0;
  id_ex_branch <= 0; id_ex_jal <= 0; id_ex_jalr <= 0;
  id_ex_mem_read <= 0; id_ex_mem_write <= 0;
  id_ex_reg_write <= 0; id_ex_halt <= 0;
end
// b) solo reset -> 0: pc, operandos, imm,
//    funct3, alu_op... (en una burbuja da igual)

Una instrucción con esos bits en 0 no salta, no toca memoria, no escribe ni genera dependencias. El flush pasa de unas 190 a 22 flip-flops. El reset sigue llevando todo a 0.

Clock Wizard y UART

El IP clk_wiz_cpu (un MMCM) genera 85 MHz a partir del oscilador de 100 MHz y los distribuye por la red global (BUFG). No es clock gating: es otro reloj sintetizado por hardware dedicado. Mientras no engancha (locked = 0), todo queda en reset. Se eligió 85 MHz y no 90 para dejar margen al ruteo completo y al jitter, y porque le conviene a la UART:

localparam CLK_HZ = 85_000_000;
localparam DVSR   = (CLK_HZ + 8*BAUD) / (16*BAUD);  // 46,1 -> 46
// error de baudios: 0,24 %   (a 80 MHz serían 43,4 -> 43: 0,94 %)

¿Y resolver los saltos en ID?

Baja la penalidad de un salto tomado de 2 ciclos a 1, pero el salto necesita sus operandos un ciclo antes: aparecen stalls nuevos (+1 si la instrucción anterior es de ALU, +2 si es un load) y hace falta forwarding hacia ID. Estimado con el modelo de referencia:

Preguntas para la defensa

  1. ¿Cuál es el camino crítico?Antes: un load seguido de un salto que usa el dato. Lectura de la BRAM, mux de WB, forwarding, resta de la ALU, zero, branch_taken y flush de ID/EX. Ahora: lectura de la BRAM, forwarding, ALU (slt) y EX/MEM.
  2. ¿Por qué la frecuencia sale de post-síntesis?Lo indicó el docente: depende solo del diseño, no de una corrida de place & route en particular. Post-route da un poco más (96,5 MHz) porque el ruteo real resultó mejor que la estimación.
  3. ¿Cómo se calcula fmax a partir del WNS?Con un reloj de período T, el camino más lento mide T − WNS. fmax = 1 / (T − WNS).
  4. ¿Por qué el comparador es más rápido que la ALU?a == b son 32 XOR y un árbol de AND, unos 3 niveles de LUT o la cadena de acarreo. La resta pasa por el mux ALUSrcB, un sumador de 32 bits, el mux de resultado de la ALU y un OR de 32 bits para zero.
  5. ¿Es correcto no limpiar los datos en una burbuja?Sí: lo que hace una instrucción lo deciden sus bits de control. Con branch, jal, jalr, mem_read, mem_write, reg_write y halt en 0, y rs1/rs2/rd en 0, no tiene ningún efecto aunque sus operandos tengan cualquier valor. El reset sí pone todo en 0.
  6. ¿Hay skew?Hay un solo reloj, distribuido por la red global. El análisis de timing incluye el skew de cada camino: −0,011 ns en el crítico, despreciable.
  7. ¿Por qué 85 MHz y no 90?Margen para el ruteo y el jitter del MMCM, y un error de baudios de la UART de 0,24 %. Con el diseño completo, WNS = +0,59 ns: llegaría a ~89 MHz.
